# حقيقة تشخيص المشروع وخطة العلاج الإلزامية — D-308

> **الحالة:** OPEN / BLOCKED_FOR_PRODUCTION_CLAIMS
> **تاريخ القياس:** 2026-10-04
> **النطاق:** checkout كامل للمستودع، مع فصل ما قيس محلياً عما يحتاج Python 3.12 أو خدمات خارجية.
> **السلطة:** هذه الوثيقة تصف الحالة؛ القانون والإنفاذ في `docs/architecture/VIBE_CODING_PREVENTION_CONSTITUTION.md` و`docs/governance/PROJECT_REMEDIATION_PLAN.json`.

## 1. الحكم

المشروع يملك حوكمة واسعة ومتصلة بالـ CI، لكن لا يجوز إعلان الجاهزية التشغيلية. العطب الأعلى أولوية هو **خطر الثقة الزائفة**: البيئة المحلية Python 3.11 بينما الكود يستهدف Python 3.12، و`python -m compileall` يفشل في ملفات كثيرة، كما أن `scripts/ci_guardrails.py` طبع أخطاء parse ثم انتهى `PASS`. هذا يعني أن فحصاً مهماً قد لا يشهد بما لم يقرأه.

الحالة المركبة:

| المحور | الحالة المقاسة | الحكم |
|---|---|---|
| الحوكمة والذاكرة | PASS | لا يثبت runtime |
| توافق البيئة | FAIL محلياً | Python 3.11 لا يقرأ صياغة 3.12 |
| compile كامل | FAIL محلياً | لا يوجد برهان بناء محلي صحيح |
| guardrails parse honesty | BLOCKED | أخطاء قراءة ظاهرة مع exit ناجح |
| الاختبارات | UNVERIFIED | pytest غير مثبت محلياً |
| runtime والإنتاج | UNKNOWN | لا ادعاء بلا probe حي |
| placeholders/TODO | OPEN | تحتاج تصنيفاً وربطاً بالمسارات |
| ازدواجية app/microservices | RISK | مصادر حقيقة متنافسة محتملة |

## 2. الأدلة القابلة لإعادة التشغيل

```text
python --version                         -> Python 3.11.2
python -m compileall -q REPOSITORY_PATHS -> FAIL (صياغة Python 3.12)
python scripts/ci_guardrails.py           -> PASS مع Error parsing متعدد
pytest --collect-only -q                  -> UNAVAILABLE (pytest غير مثبت)
check_memory_coherence.py                 -> PASS
check_vibe_coding_constitution.py        -> PASS
check_engineering_governance.py          -> PASS
```

أمثلة الصياغة غير القابلة للتحليل تحت 3.11:

- `type RouterSpec = TYPE_EXPRESSION`
- `class Stack[T]:`
- `def inject with type parameter T`

هذا ليس حكماً بأن الصياغة خاطئة تحت 3.12؛ إنه حكم بأن التشغيل المحلي الحالي غير صالح لإصدار الشهادة.

## 3. المخاطر الجذرية

### R1 — بيئة تحقق غير موحدة (C0/C3)

الـ CI يستهدف 3.12، بينما بيئة التشخيص الحالية 3.11. أي نتيجة parse أو import محلية قد تكون غير ممثلة للبيئة المعتمدة.

### R2 — فشل parser لا يُحوّل بالضرورة إلى فشل بوابة (C0)

ظهور `Error parsing` مع نجاح `ci_guardrails.py` يخلق ضماناً زائفاً. يجب أن يكون عدم القدرة على القراءة حالة فشل قاطعة، لا تحذيراً.

### R3 — الاختبارات غير مثبتة محلياً (C3)

لا توجد نتيجة اختبار محلية قابلة للتكرار في هذه الجولة؛ عدد ملفات الاختبار ليس دليلاً على نجاحها.

### R4 — قدرات ناقصة أو مؤجلة (C2/C3)

توجد `NotImplementedError` و`TODO` في خدمات وقواعد بيانات وVault وجسور وخدمات ذات صلة بالمسار. يجب منع تسميتها ACTIVE دون import + call chain + runtime evidence.

### R5 — ازدواجية مصادر الحقيقة (C3)

توجد طبقات متشابهة في `app/` و`microservices/`؛ يجب إثبات العقد والمصدر القانوني لكل نوع/بروتوكول/قرار، ومنع الانحراف الصامت.

## 4. العلاج الإجباري — لا ترقية ولا ادعاء قبل الإغلاق

الأولوية 0: تثبيت Python 3.12 في devcontainer وMakefile وCI، وإعلان `requires-python`، وإضافة فحص مبكر يرفض 3.11 برسالة صريحة.

الأولوية 1: تعديل `ci_guardrails.py` أو مسار استدعائه بحيث يتحول كل `SyntaxError`/فشل قراءة إلى exit غير صفري؛ إضافة اختبار سلبي يثبت أن ملفاً غير قابل للتحليل يجعل البوابة حمراء.

الأولوية 2: تشغيل compile، lint، type-check، collection، unit، contract، integration، security، وsmoke تحت Python 3.12 مثبت؛ لا تُكتب PASS قبل تنفيذها.

الأولوية 3: بناء سجل قدرة لكل TODO/NotImplemented/مسار حساس يحدد ACTIVE/PARTIAL/DORMANT/ZOMBIE والمالك والدليل وخطة الإكمال أو التقاعد.

الأولوية 4: تحديد المصدر القانوني للعقود والأنواع والأحداث بين `app` و`microservices`؛ إضافة parity/boundary tests ومنع الاستيراد العابر غير المبرر.

الأولوية 5: تشغيل probes حقيقية مع بيانات اصطناعية فقط، وإثبات rollback، الأسرار، العزل، المراقبة، ومسارات الفشل قبل أي ادعاء إنتاجي.

## 5. قاعدة الوكيل

كل وكيل يلمس المشروع أو يعتمد على مكوّن منه **ملزم** بقراءة هذه الوثيقة و`PROJECT_REMEDIATION_PLAN.json`، وتحديد remediation IDs المتأثرة، ورفض أي عمل أعلى من أساسه إذا كان blocker قائماً. لا يجوز للوكيل:

- تحويل `UNKNOWN` إلى `PASS`.
- تجاوز R1 أو R2 بتغيير صياغة التقرير.
- إضافة قدرة جديدة فوق مسار غير مثبت.
- إغلاق remediation دون دليل قابل لإعادة التشغيل.
- إعلان الإنتاج قبل أن تصبح الأولويات الحرجة `CLOSED` بمراجعة مستقلة.

## 6. التشخيص البنيوي المستخلص من صورة المنزل

الصورة تُظهر منزلين متشابهين من الخارج، لكن الأول يحمل تمديدات ملونة متشابكة وأساساً من أحجار غير متجانسة، بينما الثاني يملك مسارات داخلية قابلة للتتبع وأعمدة وحملاً موزعاً. تطبيقها على المشروع يحدد أربعة فواصل لا يجوز خلطها:

1. **السطح مقابل الأساس:** نجاح endpoint أو وجود مجلد Agent لا يثبت سلامة dependency path.
2. **الأسلاك مقابل الحدود:** كثرة الوحدات لا تعني استقلالها؛ الاستيراد والعقد ومسار البيانات هو الذي يثبت الحدود.
3. **الاهتزاز مقابل الفشل:** خطأ صغير في بيئة اللغة قد يجعل كل القياسات اللاحقة غير صالحة، مثل منزل يهتز قبل أن يثبت حمله.
4. **الحجارة مقابل النفايات:** TODO وNotImplemented والنسخ المكررة ليست مجرد تنظيف؛ قد تكون دعامات أو مسارات مستعملة، لذلك الحذف بلا برهان ممنوع.

النتيجة: العلاج الصحيح يبدأ من الأرضية (البيئة، parser، العقود، الاختبار، rollback)، لا من إضافة واجهة أو وكيل جديد فوقها.

## 7. حدود القياس

هذا التشخيص لا يدعي فحص GitHub branch protection، ولا صحة الخدمات الخارجية، ولا سلامة الإنتاج، ولا نجاح Python 3.12؛ هذه حالات `UNKNOWN` حتى تُقاس في بيئة مطابقة.
