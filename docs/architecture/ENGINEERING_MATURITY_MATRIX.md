# مصفوفة النضج الهندسي ذات أفق 500 سنة — D-306/EMM

> **الغرض:** تحويل سلّم «من الميلاد المعرفي إلى الحكمة الهندسية» إلى أداة تدقيق صلبة ضد قفزات Vibe Coding.
> ليست هذه الوثيقة ادعاءً بأن المشروع ناضج في كل الطبقات؛ هي مِجهر يبيّن أين توجد الأدلة وأين توجد الفجوات.
> **حكم D-306/L13:** لا يضيف أي وكيل حرفاً واحداً فوق هذه المصفوفة؛ أي قدرة تبدو مثل الصور اللامعة وفوقها أساس مجهول تُعامل كخطر بنيوي حتى تثبت طبقاتها الأدنى.

## 1) لماذا أُضيفت هذه الطبقة؟

الخطر في مشاريع الذكاء الاصطناعي والوكلاء ليس أن يكون الكود ناقصاً فقط، بل أن يبدو المشروع متقدماً لأن فيه:

- مجلدات Agents،
- عقود Microservices،
- نماذج AI،
- اختبارات كثيرة،
- وثائق طويلة،

بينما تكون الطبقات التي تحتها — المشكلة، اللغة، مصدر الحقيقة، حالات الفشل، البيانات، الأمن، الملاحظة، والتجريب — غير مثبتة بما يكفي.

لذلك أصبحت قاعدة المراجعة:

```text
لا تُقبل طبقة عليا لأنها موجودة؛ تُقبل فقط إذا كانت الطبقات المعرفية التي تحتها مفهومة ومصممة ومنفذة ومتحققة وقابلة للتطور.
```

## 2) المصفوفة الآلية

المصفوفة الحقيقية في JSON كي تفحصها البوابات آلياً:

- [`../governance/ENGINEERING_MATURITY_MATRIX.json`](../governance/ENGINEERING_MATURITY_MATRIX.json)
- [`../governance/ENGINEERING_MATURITY_AUDIT.json`](../governance/ENGINEERING_MATURITY_AUDIT.json)

الأولى تحتوي **295 checkpoint** عبر 29 مرحلة `M00 → M28`. كل checkpoint يحمل:

| الحقل | المعنى |
|---|---|
| `required_evidence.UNDERSTOOD` | ما يثبت أن الفريق يفهم الطبقة لا يردد اسمها |
| `required_evidence.DESIGNED` | ما يثبت أنها صُممت بعمد وحدود ومالك |
| `required_evidence.IMPLEMENTED` | ما يثبت أن لها موضعاً محلياً محدداً |
| `required_evidence.VERIFIED` | اختبار/بوابة/قياس/برهان سلبي |
| `required_evidence.EVOLVABLE` | خطة تغير أو تراجع أو شرط ترقية |
| `failure_signature_ar` | بصمة فشل Vibe Coding إذا غاب الدليل |
| `test_ar` | طريقة مراجعة قابلة لإعادة التشغيل |
| `pass_fail_rule_ar` | قاعدة قبول/رفض لا تعتمد على الانطباع |

## 4) تطبيقها على هذا المستودع الآن

الحالة التجارية الحاكمة لا تتغير بهذا العمل:

- القرار الحاكم: **D-300**.
- الإسفين النشط الوحيد: `fr-be-einvoicing-referential-cleansing`.
- المنصة التعليمية: **مجمّدة**؛ لا ميزات ولا هجرة خدمات ولا عمل نموذج جديد إلا ما يبقي CI صادقاً.

لذلك يطبّق التدقيق هنا كطبقة حوكمة وفحص، لا كفتحٍ لمسار منتج جديد.

القراءة المحافظة في [`ENGINEERING_MATURITY_AUDIT.json`](../governance/ENGINEERING_MATURITY_AUDIT.json) تقول باختصار:

| النطاق | القراءة |
|---|---|
| المشكلة والقيمة | موثقة بدليل قوي (`README.md`, `VALUE_DOCTRINE`, `D-300`) |
| اللغة والمعرفة المؤسسية | قوية نسبياً بفضل `.memory/`, السجلات، والفهارس |
| الاختبارات والبوابات | واسعة، لكن كل بوابة تحتاج برهان حجب لا مجرد تشغيل |
| الأنظمة الموزعة والتشغيل والملاحظة | **PARTIAL**؛ يوجد تصميم وبراهين جزئية، لا تشغيل كامل لكل الخدمات في CI |
| AI/Agents/AI Verification | **PARTIAL**؛ وجود الطبقات لا يعني نضجاً تشغيلياً عاماً، والحالة نفسها تعلن الفجوات |
| الحكمة الهندسية | مثبتة عملياً بقرار عدم البناء: D-300 يجمّد ما لا يخدم الإسفين النشط |

## 5) كاشف كارثة Vibe Coding

أي تغيير جديد يضيف طبقة عليا يجب أن يجيب:

```text
هل قفزنا من M03/M04 إلى M19/M20 دون أدلة M07→M18؟
```

مثال رفض مباشر:

```text
"أضف Agent جديداً يقرر تلقائياً ويرسل بيانات خارجية"
```

لا يُقبل حتى توجد أدلة:

- M00: لماذا توجد القدرة ولمن؟
- M02: ما اللغة والعقد؟
- M09: كيف تفشل؟
- M10: ما الصلاحيات والأسرار والعزل؟
- M14/M15: كيف تُشغَّل وتُراقَب؟
- M19/M20: ما حدود النموذج والأداة والذاكرة؟
- M21/M23: كيف نختبر الانحراف والخصم؟
- M22: أين تُحفظ المعرفة بعد انتهاء المحادثة؟

## 6) الإنفاذ

تحرس المصفوفة بوابة:

```bash
python scripts/fitness/check_engineering_maturity_matrix.py
python scripts/fitness/check_repository_microscope.py
```

وتفشل إذا:

- نقص عدد المراحل عن `M00 → M28`.
- خرج عدد checkpoint عن نطاق 200–300.
- غاب أي حقل من: الدليل المطلوب، بصمة الفشل، الاختبار، قاعدة القبول، مستوى النضج.
- حمل التدقيق دليلاً إلى ملف غير موجود.
- لم تُسجّل الوثيقة في فهرس التوثيق وبيانه الآلي.
- لم تكن البوابة موصولة بمسار `guardrails` المطلوب.

## 7) قاعدة الاستخدام اليومية

قبل أي عمل جوهري:

```text
Understand → Model → Experiment → Build → Verify → Observe → Learn → Evolve → Preserve knowledge → Repeat
```

ولا تُعلن النتيجة «ناضجة» إلا إذا أجابت الأدلة الخمسة:

```text
UNDERSTOOD?  DESIGNED?  IMPLEMENTED?  VERIFIED?  EVOLVABLE?
```

إذا كان الجواب: `IMPLEMENTED = نعم` و`UNDERSTOOD = ضعيف`، فهذا ليس تقدماً؛ هذه هي الصيغة الأخطر للـVibe Coding.

## 8) الأثر الرجعي والمستقبلي

هذه المصفوفة لا تطبّق على الكود الجديد فقط. القاعدة الدستورية هي:

```text
القديم يُدقَّق عند لمسه أو الاعتماد عليه؛ والجديد لا يدخل أصلاً قبل الدليل.
```

لذلك:

- أي ملف قديم يلمسه وكيل يجب أن يحدد أدنى مرحلة نضج متأثرة.
- أي قدرة مستقبلية يجب أن تثبت الطبقات الأدنى قبل إضافتها.
- الدين القديم لا يصبح أساساً لقدرة جديدة إلا إذا سُجّل كفجوة موروثة بمالك وحد وخطة تقليص.
- لا توجد حماية زمنية من نوع: «هذا كان موجوداً قبل الدستور».
- لا يوجد وعد من نوع: «سنطبق المصفوفة لاحقاً بعد الدمج».

تحرس ذلك بوابتان معاً:

```bash
python scripts/fitness/check_vibe_coding_constitution.py
python scripts/fitness/check_engineering_maturity_matrix.py
python scripts/fitness/check_repository_microscope.py
```
