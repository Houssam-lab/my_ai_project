## 2. طوبولوجيا الألم

```text
ROOT PAIN
«لا تمثيل قابل للتحقّق لنتيجة العمل الوكيل؛ الادّعاء سلعة ثقة»
├── Operational Pain
│   ├── Time     : أيام بين «سلّمنا» و«قبلوا» (بلا قياسٍ عندنا — H-01)
│   ├── Labor    : ساعات غير مفوترة لصنع لقطات/فيديوهات إثبات (D-01 §XIX)
│   └── Complexity: 3+ أنظمة · AI قبل فعلٍ · إعادة محاولة · تكرار (X-16 · X-17)
├── Financial Pain
│   ├── Cost         : إعادة عمل بعد قبولٍ خاطئ (X-17: 847 سجلّاً)
│   ├── Lost Revenue : دفعة نهائية محجوزة / حلولٌ مفوترة تُنازَع (X-01 · X-05)
│   └── Rework       : تصحيح بيانات downstream يدوياً
├── Risk Pain
│   ├── Failure  : فشل صامت بعد التسليم (X-16)
│   ├── Dispute  : «ما الذي يُحتسب نتيجة؟» (X-01 · X-03)
│   └── Liability: استثناءات التأمين العامّة منذ 2026-01-01 (X-08) — والمكتتب يطلب سجلاً قابلاً لإعادة التشغيل (X-10)
└── Decision Pain
    ├── Uncertainty  : «لا نعرف» يُقرأ نجاحاً حين يغيب التمثيل (C-02 يمنعه بالنوع)
    ├── Ambiguity    : النيّة البشرية غير مُصرَّفة إلى شروط (Why 3)
    └── Lack of Trust: لا يستطيع أيٌّ من الطرفين نمذجة الخطر (X-04)
```

### نقطة انهيار الألم (حيث يستطيع النظام أن يملك الألم)

الألم **لا ينهار** عند «فهم ما حدث» (تفعله أدوات التتبّع) ولا عند «إصلاح ما فشل» (يفعله المطوّر). ينهار عند **إصدار حكمٍ يقبله من يدفع** — أي عند تقاطع `Financial.Lost Revenue × Risk.Dispute × Decision.Lack of Trust`. هذه النقطة الوحيدة التي تجمع مالاً محجوزاً وطرفين لا يثق أحدهما بالآخر وغياب طرفٍ ثالث.

## 3. صيغة كلفة الحادثة/النزاع (تُملأ من بيانات العميل — لا أرقام مخترَعة)

```text
Blocked-Outcome Cost =
    blocked_amount × days_blocked × cost_of_capital_daily
  + proof_making_hours × loaded_rate
  + (dispute ? negotiation_hours × owner_rate : 0)
  + (wrong_acceptance ? downstream_cleanup_hours × ops_rate + duplicate_actions × unit_cost : 0)
  + (lost_renewal ? renewal_value × P(loss) : 0)
```

**القاعدة:** لا يُقتبس مكوّنٌ لم يُملأ من مقابلةٍ مؤرَّخة. المكوّنات الثلاثة الأولى **قابلة للقياس في أوّل pilot** (H-02)؛ الأخيران تخمينٌ حتى يُصرّح بهما المشتري.

## 4. البحث عن العمليات غير المخدومة (Unserved Workflow Search)

الشروط السبعة: النتيجة مهمّة · تنفيذ متعدّد الخطوات · آثار جانبية · فشلٌ مكلف · النجاح غير واضح من السجلّات · فارق بين النجاح التقني والتجاري · نزاعٌ محتمل حول «هل تمّ؟».

| الـworkflow | مهمّة | متعدّد | آثار | مكلف | غامض في السجلّ | تقني≠تجاري | نزاع | حالة downstream قابلة للقراءة | الحكم |
|---|---|---|---|---|---|---|---|---|---|
| Lead intake → AI qualification → CRM → owner → notify | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ (تعريف «مؤهَّل») | ✓ (CRM API) | **أوّل** |
| Support resolution (تذكرة → وكيل → إغلاق) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ (72h quiet) | ✓ (X-01) | ✓ (ticket API) | **ثانٍ** — ground truth أصعب |
| Appointment booking (AI voice → calendar → CRM) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ (حضور) | ✓ (X-06) | ✓ (calendar + CRM) | ثالث — صوت/async |
| Invoice extraction → ERP draft | ✓ | ✓ | ✓ | ✓✓ | ✓ | ✓ | ✓ | ✗ غالباً (وصول ERP) | لاحقاً |
| Payment → fulfillment | ✓ | ✓ | ✓✓ | ✓✓ | ✓ | ✓ | ✓ | ✗ (خطر لا يُقبل أولاً) | مرفوض أولاً |
| Content publishing | ✗ | ✓ | ✓ | ✗ | ✓ | ✗ | ✗ | ✓ | ألمٌ ضعيف |

**أفضل مكان لإدخال الحكم:** عند **حدّ النظام-المسجِّل (system of record)** — الحالة بعد الفعل تُقرأ للقراءة فقط عبر API، وتُقارن بمحمولٍ متّفقٍ عليه قبل التنفيذ. هذا يجعل الحكم مستقلاً عن سجلّات الـworkflow نفسها (وهي ما لا يثق به الطرف الآخر).

## 5. ما يُصنَّف ألماً موروثاً (لا يُبنى عليه)
